1. 第1章说明目标用户、具体问题、工业软件价值及机械设计、几何建模、AI、软件工程的交叉；区分已有demo、拟新增能力和已验证结果。

3. 与刘子轩比较人工CAD建模、在现有插件基础上扩展、自研或训练生成模型三条路线。第2章解释选择依据，4.4提供计算，假设及数字共用一个版本。
4. 第3章形成章程、干系人登记册、真实启动记录。批准日期、签名和会议内容按实际资料填写；缺失项在群内对话中提出，不补造。
5. 4.1提交49个子过程裁剪表，逐项说明保留、合并、简化或本阶段不展开的理由、报告落点和产物。将采购、资源、配置和变更管理安排到明确章节，避免机械套用。
6. 在4.1规划后续执行、监控、收尾：责任人、监控对象与频率、升级触发条件、变更确认、验收和遗留项处理、归档总结。使用计划语态。
7. 确认故事点和人时的基线、范围变更及关键结论；汇总AI说明和参考资料，统一章节、术语、图表编号与版式。

### 2.3 刘子轩

1. 提交讨论三与四的估算对照，记录数值、范围差异、依据和排期影响。故事点与人时分列，不按固定比例换算。
2. 以三次迭代、每次两天为现有基线评估可行性。开发日期未确认时使用第1—6天，不把报告截止日写为开发结束日。
3. 活动表、依赖关系、资源安排和甘特图使用常诚的WBS编号；甘特图体现并行、主责、里程碑、联调和验收窗口，附工具源文件。
4. 核对首迭代66人时任务、72人时有效容量及每人12小时上限。PO和SM管理工作单列。关键人员无余量时说明阻塞与调整方案。
5. 与余智皓逐项判断22人时风险工作是原任务已含、需要新增还是条件触发，写明对应任务和去重理由，不把22小时一律叠加。
6. 成本区分现金支出与人力机会成本，列数量、单价、公式和依据，包含适用的API、GPU、数据准备及风险储备。
7. 三方案比较至少包括总成本、预期节省工时、盈亏平衡和敏感性。未实测输入明确为情景假设，收益不能写成实际成果；结论由许祖嘉确认。

**验收：** 表内及跨表总数可复算，排期不超过个人容量，依赖合理；无法满足的计划明确提出调整，不以乐观措辞掩盖缺口。

### 2.4 余智皓

1. 质量计划覆盖需求评审、代码审查与检查、接口联调、正反例、回归、缺陷处理及完成定义。
2. 分开记录US验收与阶段目标验收；几何合法、尺寸符合、外部CAD可打开分别核验，演示成功不能代替全部AT通过。

4. 与刘子轩核对22人时的计入方式，与常诚关联WBS及AT；“监控中”等原记录状态需注明来源日期，不视为已验证风险处理有效。

6. 每张CodeArts截图附项目、操作、日期、结果、对应评分项说明及可追溯记录；截图占位不算完成。权限或工具阻塞在群内对话中提出。
7. 沟通计划写明事件、频率、参与人、渠道和输出；协作实证用真实材料呈现问题、意见、决定、后续动作，不补写虚构会议。
